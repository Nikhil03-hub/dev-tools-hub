## Deviations from the spec

**D1 — the core lives at `src/tools/curl/lib/convert.ts`, not `src/core/curl/convert.ts`.** The pure-layer gate (`scripts/check-boundaries.mjs`) forbids the *text* `fetch(` inside `src/core/**`, because core must never make a request. A cURL→fetch generator has to write that text, and a static rule cannot tell emitting from calling. Options were: weaken the rule for everyone, special-case this file, or put the emitter where the gate does not apply. I chose the third, on the existing precedent of `src/tools/json/lib/jsonParse.ts` — pure, importable, outside `src/core`. The alternative would have let a future PR add a real `fetch(` to core by editing one allowlist line. **Worth a reviewer decision, because T-212 and any later code generator will hit the same wall.**

**D2 — Python gets Python literals, not JSON text.** The spec says the JSON body is emitted in Python as "`json=` with the same JSON". JSON `true` / `false` / `null` are `NameError`s in Python 3, so following that literally would emit code that cannot run — the exact failure mode the mission warns about ("generating attractive code that silently does the wrong thing"). `pythonLiteral()` emits `True` / `False` / `None` instead. Proved by the static parse: the same output that would fail `ast.parse` as a name lookup now parses, and `{"active": true}` becomes `"active": True`.

**D3 — a value that is only a shell variable reference is not redacted.** `curl -H "authorization: Bearer $TOKEN"` is what most API docs print. `redactPair` replaces the authorization value before its own `isNonSecretValue` check can apply, so `$TOKEN` became `<AUTH_TOKEN_1>`: unusable code, plus a note claiming variables are preserved while the output proved otherwise. A variable *name* is not a secret — that is the Redactor's stated principle — so `isVariableReferenceOnly` passes `$TOKEN`, `${TOKEN}`, `%TOKEN%` and `{{ … }}` through untouched. Mixed values (`Bearer abc$TOKEN`) are still redacted, and `redactText` already protected variable references in URLs and form bodies, so this closes the one path that did not.

**D4 — repeated request headers are joined, and the join is reported.** A JS object literal with the same key twice silently keeps the last value, so `-H 'accept: a' -H 'accept: b'` would have quietly become `accept: "b"`. HTTP joins such values with commas, which is what is emitted, and a note names the header. Go uses `Header.Add`, not `Set`, for the same reason.

**D5 — small wording.** "Redacted 1 value." rather than "Redacted 1 values."; the axios output ends with `const data = response.data;` so all four targets hand back a usable result variable; `-F` gets its own warning that the emitted body is not real multipart. None of these change the API.

**Not a deviation, but worth flagging:** the spec's Detector line asks for the label "Convert cURL to code". T-106 already ships this rule with the label "Looks like a cURL command", matching all ten other detector labels, and the spec itself notes the rule is "already listed in T-106". Changing one chip's wording to differ from every other chip would be a worse product, so the shipped label stands.

## Findings for the reviewer

- **Fidelity is the feature, so the tool says what it dropped.** Options it does not carry over are listed by name (`Ignored cURL options (they do not change the request itself): --compressed, -k, -m.`), shell variables and substitutions are reported and kept verbatim, a JSON-labelled body that is not JSON is reported, `-u`/`-F`/cookie-file notes from `parseCurl` are carried through, and the parsed-fields strip separates *what was understood* from *what was generated*. The generated code is offered as a starting point, not as a guarantee that the original command's full behaviour is reproduced — which is the honest claim for any converter that does not run a shell.
- **No note can contain a secret.** There is a unit test that runs a command with two credentials and asserts neither appears in any note; notes name options and headers, never values.
- **The `--check`/`ast.parse` evidence is syntax-only.** It proves the emitted text is a valid program, not that it performs the request. A behavioural round-trip (send the original command and the generated code at the same endpoint and compare) would need a network and a server, both of which this product promises not to touch — so it is out of scope by design, not by omission.

## Limitations and what remains unverified

- **Go output is unvalidated.** No Go toolchain here, so 14 generated files were never parsed. The emitter is simple and mirrors a fixed template, but that is an assertion, not a test. A `gofmt -l` step in CI would close this cheaply.
- **Unsupported by design, per the spec's own scope:** proxy/TLS/certificate options, `--output`, retries and similar do not appear in the output (they are named in the notes); `@file` uploads are not read; multipart becomes a plain body with a warning; shell expansion is preserved as text rather than resolved; HTTP/2 and `--http2-prior-knowledge` are ignored.
- No reverse direction (code → cURL): the spec defines cURL → code only, and "Copy as cURL" in the keywords is a DevTools import path, which is supported.
- Chromium-only, as before: Firefox, Safari, iOS and a real screen reader remain unverified.
