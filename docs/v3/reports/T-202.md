## Deviations from the spec

**D1 — the time budget is applied in word and char modes too.** The spec's API note puts `timeout` on the `diffLines` call only. Measured, `diffChars` on two unrelated 40,000-character strings runs for over two seconds, and there is nothing else in the spec to stop it: the 50,000 limit is a *size* promise, and 40,000 characters is inside it. Left unbudgeted that is a frozen tab on the main thread, so every mode passes `timeout: 2000` and maps `undefined` to the spec's own sentence. Evidence: mutation M2 below, and the char-mode timeout test.

**D2 — `ignoreCase` is passed to `diffLines` as an undeclared option.** The spec asks for it; `diff@9.0.0`'s published line-options type does not list it (only `ignoreWhitespace`, `stripTrailingCr`, `newlineIsToken`, `ignoreNewlineAtEof`). It does work at runtime, measured above. The options object is built as a variable so the key passes without a cast, and a named test asserts the behaviour, so a future version that stops honouring it fails loudly instead of silently narrowing the feature.

**D3 — a 2,000-row render cap in the split view, with the truncation stated.** Not in the spec. Without it, the "tens of thousands of lines" the FAQ promises is the same sentence that would put 110,000 `<td>` cells in the DOM. The engine handles the size; the view says *"Showing the first 2,000 of 55,002 rows. Download the .patch for all of it."* and the patch is not capped.

**D4 — "Ignore case" is offered as a second toggle.** The spec names an "Ignore whitespace" Toggle; the API it specifies also takes `ignoreCase`, and a diff tool that accepts the option but gives no way to reach it would be dead weight on the surface. It is a real control with real behaviour, not a hidden parameter.

## Findings for the reviewer

- The patch is generated from the **same pair that is on screen** (`activeA`/`activeB`), not from the live text, and is built on demand rather than in a memo keyed on the text. Two things I got wrong in my first draft of the component and fixed before the suite ran: a `useMemo` whose dependency was a freshly-built object (so every render re-diffed, defeating the debounce), and a patch memo keyed on live `a`/`b` (so every keystroke paid a full diff even in line mode).
- `unifiedPatch` takes no `timeout` in the spec's signature, so it is computed without one. It only runs after `computeDiff` has already proved the same pair diffs inside 2 s, and only on a button press, so it cannot reach the pathological case the budget guards. Noted rather than changed because the signature is the contract.

M1–M3 ran against `vitest` (each failure was exactly one named test, never a collateral one). M4 was run as a standalone browser probe, described below, because the first attempt to prove it through the whole suite is itself the most useful finding of this task.

### The suite cannot survive a UI mutation — and now it can

The first M4 attempt mutated the source and ran `npm run test:e2e`. With the manual button deliberately absent, the suite reached `p.getByTestId("text-diff-run").click()`, waited 30 s, threw `TimeoutError`, and printed `FATAL` — **but the process never exited**, because `browser.close()` sits at the end of `main()` and the rejection skipped it. The open browser kept the event loop alive, held port 4173, and reported nothing. That is how a mutation run turned into a 30-minute silence.

Two changes came out of it:

1. [test/e2e.cjs](../../../test/e2e.cjs) now holds the browser at module scope and closes it in a `.finally()`, so a fatal failure exits with its error instead of hanging. This is a harness fix, not a relaxation: no assertion changed, no threshold moved.
2. M4 is proved with a probe that asserts **presence** rather than clicking, so a broken guard reports `BROKEN` and exits 1 in seconds. It also caught an arithmetic error in my own expectation — the split view renders 8,000 cells, not 4,000 (2,000 shown rows × 2 cells × 2 columns). The cap was right; my number was wrong.

A whole-suite mutation run remains available for future work; it is no longer a hang risk.


## Limitations and what remains unverified

- Side-by-side row alignment is only done for line mode; word and char use the two-tint inline rendering in both views, because aligning "half a word" into a left and right row has no honest meaning.
- `stripTrailingCr` is not exposed, so a CRLF text pasted against an LF text still shows every line as changed. That is the library default and the spec does not ask for it; worth a toggle in a later task, not invented here.
- Firefox/Safari and a real screen reader remain unverified, as at CP1.
