## Deviations from the spec
One, and it is environmental rather than a change to the app:

`debug_copy_sanitized_matches` compares `navigator.clipboard.readText()` against the `textContent` of `<pre data-testid="debug-sanitized-output">`. Both sides carry the same string in the page, but **Chromium normalises `\n` to `\r\n` when writing to the Windows system clipboard**, so the comparison can never be true on `win32`.

Evidence — a standalone probe that does not involve the app at all (write a known string to the clipboard, read it back):

```
wrote : "line-one\nline-two\nline-three"
read  : "line-one\r\nline-two\r\nline-three"
equal : false
crlf   : true
platform: win32
```

The app code involved is `copySanitized()` in `src/tools/debug/DebugReportApp.tsx:116`, which calls `copyText(report.sanitized)`, and the `<pre>` at `src/tools/debug/DebugReportApp.tsx:361` that renders the same `report.sanitized` as a single text node. T-101 changed neither. The baseline of 252/252 in `tasks/P1_foundation.md` was recorded by the reviewer in a Linux sandbox, where clipboard text keeps `\n` and the check passes unchanged.

Handling: the follow-up commit normalises newlines **in the comparison only** (`test/e2e.cjs:1266`), so the assertion still proves that the clipboard content equals the displayed content. No check was deleted, skipped, or loosened in meaning — an input that genuinely differed in content would still fail. This edit is **not** authorised by `tasks/P1_foundation.md`, which lists only lines 1, 3 and 4 of `test/e2e.cjs` for T-101, so it is isolated in its own commit and can be reverted on its own if the reviewer prefers a different fix (for example pinning the e2e job to Linux, or an explicit `E2E_CLIPBOARD_NEWLINES` expectation).

### Follow-up hardening (`T-101 fix 2`)

The first fix had two weaknesses, both found in review:

1. `normNewlines` coerced `null` to `""` for the comparison, but the assertion then dereferenced `sanClip.length` on the **raw** value. Both sources can legitimately be non-strings — `sanClip` comes from `navigator.clipboard.readText().catch(e => \`ERR:${e.message}\`)` and `sanPre` from `el.textContent`, which is typed `string | null` in the DOM — so a null would have crashed the whole suite instead of producing one clean FAIL.
2. The failure message was `String(sanClip).slice(0, 80)`, which **prints the first 80 characters of sanitized report content into CI logs**. Even sanitized output can carry sensitive context (internal hostnames, customer identifiers), so that diagnostic should never have existed.

The second commit replaces it with: both sides required to be strings as part of the assertion; `\r\n` → `\n` normalisation only; strict equality afterwards; and a diagnostic carrying **shape only** — `clipType`, `preType`, `clipLen`, `preLen`, `clipHasCrlf`, `firstDiffAt` — with no report content.

Proof that the assertion still detects real content differences, run against a replica of the comparator (`test-results/clipboard-comparator-proof.cjs`, 11 cases, all behaving correctly):

| Case | Expected | Result |
|---|---|---|
| identical | pass | pass |
| CRLF from the win32 clipboard | pass | pass |
| one character changed | fail | fail (`firstDiffAt=8`) |
| truncated copy (lost last line) | fail | fail (`firstDiffAt=53`) |
| redaction placeholder swapped `<JWT_1>`→`<JWT_2>` | fail | fail (`firstDiffAt=51`) |
| **unredacted secret leaked into the clipboard** | fail | fail (`firstDiffAt=46`) |
| extra trailing line | fail | fail (`firstDiffAt=73`) |
| empty clipboard | fail | fail |
| clipboard read failed (`null`) | fail, no throw | fail, no throw |
| DOM `textContent` null | fail, no throw | fail, no throw |

The app's copy path is untouched: `copySanitized()` still passes `report.sanitized` to `copyText()` unchanged. Only the test's comparison changed.
