## Deviations from the spec

**D1 — no manual-Convert gate above 1,000,000 characters.** The shared P2 rule exists because an expensive recomputation on every keystroke janks the page. Parsing a URL is a single linear `new URL()` and cannot produce that cost; a megabyte paste is rejected or split in milliseconds. The 150 ms debounce stays. If a reviewer prefers uniformity over this reasoning, adding the button is a two-line change.

**D2 — `localhost` is special-cased.** `new URL("localhost:3000")` succeeds by reading `localhost:` as a scheme, giving an empty host — the opposite of what a developer pasting it means. Nothing else is special-cased: real and exotic schemes (`mailto:`, `data:`, `chrome-extension://`) are still handed to the parser as written, and a test asserts that.

**D3 — rebuilding encodes a space as `%20`, not `+`.** `URLSearchParams.toString()` emits `+`, which would make the spec's own round-trip example come back as `y=+z` instead of the `y=%20z` it was given. `buildUrl` therefore serialises pairs itself with `encodeURIComponent`. A test documents the counterpart: a `+` *in the input* is decoded to a space (form-urlencoded semantics, which the URL standard applies to query strings) and comes back as `%20`.

**D4 — protocol-relative `//example.com/x` is accepted.** Not in the spec; it would otherwise throw. Prepending `https:` is the reading the user means when pasting it out of a `<script src>`.

**D5 — edits are keyed to the parsed `href`.** The spec's "edit parameters in a table" does not say what happens when the URL changes underneath the table. Without this, typing a new URL while a row is edited would silently carry the previous URL's parameters into the new one. `Undo edits` appears only when a draft actually differs.

## Findings for the reviewer

- Two defects in my own UI, found by re-reading it after the browser probe passed, and fixed before the suite ran: **warnings were computed from the parsed URL rather than the edited table**, so renaming a parameter to `password` left the panel warning-free while the rebuilt URL carried a secret-named key; and a `try/catch` around `buildUrl` guarded a call that has no throw path, which is dead weight rather than safety. The warnings now derive from the rows on screen; the core still reports warnings for a freshly parsed URL, which is what the CLI and the unit tests consume. The probe had passed only because its own cases never renamed a key.
- Two behaviours I asserted and was wrong about, corrected in code rather than in the test: uppercase `LOCALHOST:3000` initially fell through the case-sensitive host check, and my first draft expected `localhost:3000` to be an error. Both are now tested in the shape the product actually wants.
- The credential card deliberately shows the username and password — they are already in the user's own clipboard, and hiding them would make the warning unfalsifiable. The warning text is what does the protective work: "avoid sharing this URL."

## Limitations and what remains unverified

- Editing is limited to query parameters, as specified; protocol, host, path and fragment are read from the input and shown, not editable.
- `URL` normalises hosts (case, punycode, default ports) and resolves `.`/`..` in paths, so a rebuilt URL is the *normalised* form rather than a byte-for-byte echo of exotic input. Tests pin the cases that matter; none of it is a network resolution.
- Chromium only, as before.
