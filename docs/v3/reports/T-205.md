## What it does

Parses nothing itself. Validation and the English sentence come from cronstrue (tried first, and its message is what the user sees on rejection); the future times come from croner, evaluated in the chosen zone; this module expands macros, builds the field table, formats the offsets and refuses what it cannot honestly describe.

Boundaries it enforces: an expression over 500 characters is refused rather than processed; the run count is clamped to 1–20; a zone the engine cannot format is reported as unknown; and 7-field Quartz expressions are refused with an explanation instead of being quietly misread.

## Deviations from the spec

**D1 — `@DAILY` is accepted by canonicalising the macro.** cronstrue reads `@daily` but throws "Unknown special expression." for the uppercase form, while croner is more permissive. Rather than let the two libraries disagree, a recognised macro is expanded first and the expansion is what both are given. That also makes the description and the field table agree by construction.

**D2 — 7-field expressions are refused.** cronstrue silently accepts `0 0 0 * * * *` and describes it as "Every hour", dropping a field on the floor. Per the mission's "do not silently interpret syntax using a different dialect", this tool states that it reads the standard 5-field and 6-field-with-seconds forms and points at Quartz explicitly.

**D3 — the detector requires one structured field.** The spec's rule allows `^[A-Za-z]+$` per field, which makes *"the quick brown fox jumps"* a five-field schedule. Requiring at least one field to contain a digit or one of `*,/-?` keeps every real expression (including `0 0 * * MON`) and rejects sentences; both directions are tested.

**D4 — the zone check asks `Intl`, not `Intl.supportedValuesOf`.** Measured: Node 22's `supportedValuesOf("timeZone")` omits `Asia/Kolkata` even though the formatter handles it, and this machine's own resolved zone is the legacy alias `Asia/Calcutta`. A membership test would have rejected zones that work, so validation constructs `new Intl.DateTimeFormat(..., {timeZone})` — the same thing the formatter is about to do. The dropdown is still populated from `supportedValuesOf` (420 options measured), with UTC and the fallbacks added.

**D5 — "Copy output" copies a summary, not a single field.** An explainer has no one output artefact: the description, the zone it was computed in and the run list are the result. The button says "Copy summary" and the clipboard is asserted to equal exactly that block.

**D6 — no manual-Convert gate above 1,000,000 characters.** As with T-204, the shared rule defends against an expensive recompute; cron parsing is bounded by the 500-character limit and croner's run search is capped at 20 runs, so the debounce is the only pacing needed.

## Findings for the reviewer

- **Two test bugs the pre-suite probe caught.** My first `cron_copy` assertion counted offsets with `ISO.match(/^…$/g)`, and an anchored pattern under `/g` can match at most once — the assertion would have "passed" by counting 1 of 5, or failed for the wrong reason. It now compares the clipboard to a constructed expectation and counts with an unanchored copy of the pattern. The zone-change test also asked the dropdown for `Asia/Kolkata`, which is not necessarily offered; it now uses `Pacific/Kiritimati`, which is +14:00 all year and so cannot drift with DST.
- **Three expectations of mine were wrong arithmetic, not code bugs.** For `Asia/Kolkata` and `Asia/Kathmandu` I had written the UTC instant where the wall-clock reading belongs (the whole point of the feature), and for `0 0 * * * *` I miscounted which field is seconds. The tests now assert the values the standard actually produces, each derived by hand and then confirmed.
- **DST behaviour is real, not modelled.** `30 2 * * *` in `America/New_York` from 2026-03-07 yields `2026-03-08T03:30:00-04:00`: 02:30 does not exist that morning and croner moves it forward. That is croner's semantics, inherited here, and it is asserted in a unit test so a change is visible rather than silent.

## Limitations and what remains unverified

- **Dialect honesty:** the supported grammar is the intersection of what cronstrue and croner accept, which covers Vixie/standard cron plus the `?`, `L`, `W` and `#` extensions **in the fields where they are meaningful** (`0 0 L * *` explains as "on the last day of the month"; `L` in the minute field is rejected). Jenkins' `H` is not supported: the detector offers the chip, and the explainer then says `Expression contains invalid values: 'H'`, which is the intended outcome.
- **The two libraries disagree on one thing, and it is visible.** `5-1 * * * *` is a reversed range: cronstrue happily describes it ("Minutes 5 through 1 past the hour") while croner refuses it (`CronPattern: From value is larger than to value`). Because the run times are the part a user would act on, croner's veto decides the result and the tool reports an error rather than a description of a schedule it cannot compute. Asserted in a unit test so the disagreement cannot be silently resolved the other way by an upgrade.
- Runs are computed forward from *now* in the browser (the core takes `from` explicitly, so tests control time; the UI does not fabricate a fixed date).
- Chromium only: Firefox, Safari, iOS and a real screen reader remain unverified, as at CP1.
